## 1. Why

The current seed (8 members, a few plots/payments/dealers) is too small and too
sparse to feel real, so the poisoning demos don't land emotionally — there's no
"that's a real person's money / that's a real exporter's bank detail" moment.
200 members + a corporate buyer layer makes the database read like a cooperative
that actually exists, which is what makes the attacks land in the room.

## 3. Schema additions

Add PII to `members` (today it has no name column at all — the CSV's `name` is
currently dropped):

```sql
ALTER TABLE members ADD COLUMN full_name     TEXT;
ALTER TABLE members ADD COLUMN national_id   TEXT;   -- fake, fixed prefix
ALTER TABLE members ADD COLUMN date_of_birth DATE;
ALTER TABLE members ADD COLUMN sub_county    TEXT;
ALTER TABLE members ADD COLUMN village       TEXT;
ALTER TABLE members ADD COLUMN next_of_kin        TEXT;
ALTER TABLE members ADD COLUMN next_of_kin_phone  TEXT;
ALTER TABLE members ADD COLUMN joined_on       DATE;
ALTER TABLE members ADD COLUMN status          TEXT DEFAULT 'active';  -- active | inactive | deceased
ALTER TABLE members ADD COLUMN phone_changed_on DATE;                  -- NULL unless stale (mess)
```

New corporate tables:

```sql
CREATE TABLE buyers (
  id SERIAL PRIMARY KEY,
  buyer_code TEXT UNIQUE NOT NULL,        -- e.g. BUY-0007
  name TEXT NOT NULL,                     -- "Rift Valley Coffee Exporters Ltd"
  country TEXT NOT NULL,
  contact_name TEXT, contact_email TEXT, contact_phone TEXT,
  bank_name TEXT, bank_account TEXT, settlement_swift TEXT,   -- the "leakable" bit
  kra_pin TEXT                            -- fake Kenyan tax PIN shape
);

CREATE TABLE contracts (
  id SERIAL PRIMARY KEY,
  contract_ref TEXT UNIQUE NOT NULL,
  buyer_id INT REFERENCES buyers(id),
  season TEXT NOT NULL,
  kilos REAL NOT NULL,
  price_per_kg_usd NUMERIC(8,2) NOT NULL,
  incoterm TEXT,                          -- FOB / CIF
  signed_at DATE, status TEXT             -- draft / signed / settled
);
```

Operational back-office tables (what makes it feel like a real factory system):

```sql
CREATE TABLE deliveries (            -- cherry weighed in at the factory
  id SERIAL PRIMARY KEY,
  member_id INT REFERENCES members(id),
  season TEXT NOT NULL, delivered_on DATE NOT NULL,
  kilos REAL NOT NULL, grade TEXT, factory TEXT
);
CREATE TABLE advances (              -- cash / input credit against future crop
  id SERIAL PRIMARY KEY,
  member_id INT REFERENCES members(id),
  kind TEXT NOT NULL,                -- cash | fertiliser | pesticide
  amount_kes NUMERIC(12,2), issued_on DATE, status TEXT,   -- outstanding | repaid | written_off
  dealer_licence TEXT REFERENCES dealers(licence_no)
);
CREATE TABLE grading (               -- mill / quality records per lot
  id SERIAL PRIMARY KEY,
  lot_ref TEXT UNIQUE NOT NULL, member_id INT REFERENCES members(id),
  season TEXT, grade TEXT,           -- AA | AB | PB | C | TT
  cupping_score REAL, outturn_pct REAL, milled_on DATE
);
CREATE TABLE sacco (                 -- member savings / loan balances (financial PII)
  member_id INT PRIMARY KEY REFERENCES members(id),
  savings_kes NUMERIC(12,2), loan_balance_kes NUMERIC(12,2),
  loan_status TEXT, last_statement DATE
);
```

`reset.sh`'s TRUNCATE adds `buyers, contracts, deliveries, advances, grading,
sacco` (and the loader inserts them). Payments become **derived** from
deliveries (kilos × rate), so the numbers reconcile the way a real system's do.

## 4. The generator: `scripts/seedgen.py`

```bash
scripts/seedgen.py --members 300 --seed 42
#   writes: members.csv payments.csv plots.geojson dealers.csv products.csv
#           buyers.csv contracts.csv deliveries.csv advances.csv grading.csv
#           sacco.csv   (into data/seed/)
```

- **Deterministic**: a fixed `--seed` (default 42) so every regeneration is
  identical — reproducible demos, clean diffs.
- **Referentially consistent**: payments, plots and contracts reference real
  members/buyers; no dangling FKs.
- **Tunable**: `--members`, `--buyers`, `--seasons`, `--seed` flags.
- **Fixtures pinned**: the attack rows (see §6) are written verbatim regardless
  of the RNG, so the scenes never break on a reseed.
- Pure standard library (name pools inline), so it runs anywhere with no deps.

## 5. Record shapes and fake-PII rules

Realistic **shape**, obviously-synthetic **values** — it must never look like
real data that leaked:

- **Names**: Kikuyu/Kenyan first + last name pools (Wanjiku, Kamau, Njeri,
  Mwangi, Gichuru…), combined by the seeded RNG.
- **Phones**: `+25470` + a 6-digit block from a reserved test range, all unique.
- **National ID**: fixed fake prefix (e.g. `99` + 6 digits) so it's clearly not a
  real Kenyan ID series.
- **Emails**: `contact@<slug>.example` / `.test` — reserved, non-routable domains.
- **Payout refs**: `MPESA-07xx…` style, matching the existing `payout_account_ref`.
- **Locations**: real Kirinyaga sub-counties (Mwea, Gichugu, Ndia, Kirinyaga
  Central) + invented village names.
- **DOB / joined_on**: plausible ranges (adults; joined within the last ~15y).
- **Bank/SWIFT/KRA PIN** (buyers): correct shape, fake values, documented as such
  in a header comment.

A one-line banner comment in every generated CSV: "SYNTHETIC — generated by
seedgen.py, not real people or companies."

### Controlled messiness (what makes it read as real, not demo)

Real back-office data is dirty, and the mess also gives an attacker cover. The
generator injects a bounded, seeded amount of realistic dirt — never on the
pinned fixtures (§6), only on the generated population:

- ~8% of members **inactive** (a `status` column: active | inactive | deceased)
  — some still have outstanding advances, which is itself a finding.
- ~5% with a **missing or stale phone** (blank `phone_e164`, or a flagged
  `phone_changed_on`), so SMS-dependent flows have real edge cases.
- ~3% **duplicate-ish registrations** (same name + village, different grower
  code) — the kind of thing a laundering attack hides behind.
- Inconsistent casing / spacing in a few free-text fields (names, villages).
- A handful of members with **no plot** or **no payments yet** (newly joined).
- A few **advances written off** and **payments held** — status variety, not all
  happy-path.

All mess is deterministic (seeded) and capped, so counts are stable and the
pinned attack fixtures stay pristine.

## 7. Making the corporate data poisonable

Seeding buyer/contract rows is not enough on its own — the assistant can only
*leak* what something surfaces to it. Options (Phase 2, optional):

- **A read-only tool** `lookup_buyer` / `lookup_contract` on kahawa-tools, so a
  prompt-injection can try to make the agent fetch and reveal a buyer's bank
  details — stopped (hardened) by the tool gate / provenance. *(gateway + MCP
  change — I'll ask before building.)*

  is retrievable and an injected doc can try to exfiltrate it via retrieval.
- Both give you a "leak corporate PII/financials" scene to pair with the farmer
  payout scene. Recommend starting with the trusted-document route (no code), add
  the tool later if you want the tool-gate angle.

## 9. Risks and how we avoid them

- **Schema recreate**: adding columns/tables means the `members` table must be
  migrated or recreated. `reset.sh` already recreates on provider switch; I'll
  make the schema change additive (`ALTER … ADD COLUMN`, `CREATE TABLE IF NOT
  EXISTS`) so a reseed doesn't drop embeddings unnecessarily, and give you the
  one command to apply it.
- **EMBED_DIM / chunks** untouched — the vector table is unrelated to this.
- **Phone uniqueness & hash**: generator guarantees unique phones; `_seed.py`
  keeps computing `phone_hash` so UI lookups still match.
- **PII realism vs safety**: reserved/`.example` domains, fake ID prefixes, test
  phone ranges, and a SYNTHETIC banner — realistic shape, impossible to mistake
  for real records.
- **Fixtures drift**: pinned verbatim and asserted by a post-generate check in
  `seedgen.py` (fail if KG-0003 isn't in the forest, etc.).
- **Scenes**: unchanged; the fixtures and the KG-0001..0008 phones are preserved.
